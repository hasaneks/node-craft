# API security and data protection

## Input

- All external input is untrusted: body, query, path, headers, cookies, files, webhook payloads, provider responses.
- Parameterized queries only. Never build SQL from strings with user input; sort and filter fields come from an
  allowlist mapped to column names.
- Limits on everything: body size (`bodyLimit`), URL and header size, number of items in a batch, file size, array
  lengths and string lengths in schemas, page size.
- Use the validator's protections: reject or strip unknown properties (`additionalProperties: false`; in Fastify
  this strips unless Ajv `removeAdditional` is `false`), Fastify's
  secure JSON parser defaults against `__proto__` and `constructor.prototype` pollution, no user-controlled regex,
  and no catastrophic-backtracking patterns in your own schemas.
- File paths and object keys are generated by the server; user input never becomes a path segment without strict
  validation (no `..`, no absolute paths).

## Transport and headers

- TLS on every production connection, including the database and Redis when they leave a private network. Never set
  `rejectUnauthorized: false` or `NODE_TLS_REJECT_UNAUTHORIZED=0` in production.
- CORS lists the real web origins per environment. Wildcard CORS is not protection, and CORS does not protect mobile
  or server-to-server calls at all.
- Behind a proxy (Railway), configure the trusted proxy setting to the known hop count or ranges so `request.ip` and
  protocol are correct. Do not trust every `X-Forwarded-For` value.
- Security headers with `@fastify/helmet` (or the Nest equivalent) where responses reach browsers.

## Rate limits

- Login, token exchange, OTP, password reset, search, uploads and expensive endpoints get limits. Key by user, tenant
  and operation cost as well as IP.
- An in-process limiter is per replica. With more than one replica, use a shared store (Redis) for limits that must
  be global, and decide what happens when that store is down (`references/redis.md`).
- Over-limit answers 429 with `Retry-After` (`node-craft-contract` → `references/errors.md`).

## Outbound requests (SSRF)

When the server fetches a URL a user supplied (webhook targets, image import, link previews): allow only `https`,
resolve DNS and reject private, loopback, link-local and metadata ranges (IPv4 and IPv6), re-check after each
redirect or disable redirects, pin the resolved address for the connection, set a timeout and response size limit.

## Secrets and personal data

- Central log redaction: `authorization`, `cookie`, `set-cookie`, passwords, tokens, API keys, and personal fields
  the project marks as sensitive (`node-craft-arch` → `references/observability.md`).
- Errors never include SQL, table names, stack traces, tokens, connection strings or raw provider errors.
- Minimize personal data by purpose. Each personal field has a retention period and an account-deletion behaviour;
  backups make deletion eventual, so document how long.

## Audit

Keep audit records for permission changes, admin actions, access to sensitive data, entitlement changes and data
deletion: who, when, which resource, which action, result. Audit records are separate from debug logs, append-only
for the application, and do not store full sensitive payloads.

## Vulnerability reports

Investigate dependency and scanner alerts. Fix with the smallest verified change (patch or minor upgrade, or a
documented mitigation). Do not silence alerts, skip tests or jump majors blindly to make a scanner green.
